# Design Decisions

Each entry records what we decided, what else we considered, and why.

---

## 1. Run PostgreSQL locally via Docker Compose
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Run the dev database as a `postgres` container defined in `docker-compose.yml`, with credentials taken from a git-ignored `.env` file and data kept in a named volume (`pgdata`).

**Alternatives:**
- Install PostgreSQL directly on Windows.
- Use a cloud database (Neon/Supabase) during development.

**Why:** One command (`docker compose up -d`) gives every developer the same database version and settings, with nothing installed on the OS. A cloud DB would need internet access and would be shared. The named volume keeps data across restarts, and the healthcheck tells us when Postgres is actually ready to accept connections.

---

## 2. PostgreSQL 17 instead of 18
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Pin the image to `postgres:17` (a major version, so we still get minor/security updates).

**Alternatives:**
- `postgres:18` (newest major).
- `postgres:latest` (unpinned).

**Why:** Our planned production hosts (Neon/Supabase) fully support 17, so dev and prod stay on the same major version. The 17 image also uses the familiar data directory (`/var/lib/postgresql/data`), whereas 18 changed the volume layout. `latest` was rejected because a silent major upgrade could break the existing data volume.

---

## 3. `spring.jpa.hibernate.ddl-auto: none`. Flyway will own the schema
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Hibernate never creates or alters tables. From Milestone 2, the schema is defined only by versioned Flyway SQL migrations (`V1__init.sql`, …).

**Alternatives:**
- `update`: Hibernate changes tables to match the entities.
- `create-drop`: Hibernate rebuilds the schema on every start.

**Why:** `update` can't safely rename or drop columns and leaves no history, and `create-drop` wipes data. Versioned migrations give a reviewable, repeatable schema history that runs the same way locally and in production. We also set `open-in-view: false` so database access happens only inside services, not while the web response is being written.

---

## 4. JVM default timezone set to UTC
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** Set the JVM timezone to UTC in two places:
- `TimeZone.setDefault(UTC)` at the start of `main()`, which covers VS Code, `java -jar`, Docker and `spring-boot:run`.
- `-Duser.timezone=UTC` in the Surefire `argLine`, which covers tests, because `@SpringBootTest` never calls `main()`.

**Alternatives:**
- Set the timezone to `Asia/Kolkata`.
- Pass `-Duser.timezone` only on the command line.
- Leave the default.

**Why:** On Windows in India, Java reports the legacy zone ID `Asia/Calcutta`. The PostgreSQL JDBC driver sends that ID when it connects, and Postgres 17 rejects it (`FATAL: invalid value for parameter "TimeZone"`), so the app couldn't start. UTC is the usual choice for servers: timestamps are stored the same way whether the app runs on a laptop or on a cloud host, and the frontend converts them to IST for display. A command-line-only flag would be easy to forget.

## 5. Hikari connection timeout of 5 seconds
**Milestone:** 1 · **Date:** 2026-11-01

**Decision:** `spring.datasource.hikari.connection-timeout: 5000` (ms).

**Alternatives:** Keep Hikari's default of 30 seconds.

**Why:** When the database is down, any request that needs a connection waits for this timeout. With 30 s, `/api/health` and every other request would hang for half a minute before failing. With 5 s, it returns `503` quickly, which is better for users and for health checks run by the hosting platform.

## 6. Schema conventions: identity IDs, TIMESTAMPTZ, enums as VARCHAR + CHECK
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- IDs are `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Every timestamp is `TIMESTAMPTZ`.
- Every enum (role, job type, drive status, application status, round result, policy type) is `VARCHAR` with a `CHECK` constraint.
- Number rules are checked in the DB: CGPA 0–10, backlogs ≥ 0, CTC > 0.
- Every constraint has a name (`uq_`, `fk_`, `ck_` prefixes).

**Alternatives:**
- `SERIAL` IDs.
- `TIMESTAMP` without a time zone.
- Native Postgres `ENUM` types.
- Validation in Java only.

**Why:** Identity columns are the SQL-standard replacement for `SERIAL`. `TIMESTAMPTZ` stores an exact instant, so it can't be misread whatever timezone a client uses. Adding a value to a native `ENUM` needs `ALTER TYPE` and is awkward in migrations, while a CHECK can be swapped in one migration, and JPA's `@Enumerated(STRING)` maps to `VARCHAR` with no extra work. DB-level CHECKs are the last line of defence even if a bug skips Bean Validation. Named constraints make error messages readable (`ck_student_profiles_cgpa`).

## 7. `applications.student_id` references `student_profiles`, not `users`
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:** The applicant FK points to `student_profiles(id)`.

**Alternatives:** Reference `users(id)`.

**Why:** Only students apply, and the profile holds the data eligibility needs (CGPA, branch, backlogs, graduation year). The FK guarantees every applicant has a profile and that an admin account can never be an applicant. Ownership checks go JWT user → `student_profiles.user_id` (UNIQUE) → profile.

---

## 8. ON DELETE RESTRICT everywhere except `drive_branches` (CASCADE)
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:** All foreign keys are `ON DELETE RESTRICT`, except `drive_branches.drive_id`, which is `ON DELETE CASCADE`.

**Alternatives:**
- CASCADE on all parent → child links (for example drive → applications, round → results).
- `SET NULL`.

**Why:** In v1 we close or deactivate things instead of deleting them: a drive with applicants becomes `CLOSED`. RESTRICT makes a mistaken delete fail loudly instead of silently erasing applications, round results or audit history. `drive_branches` rows mean nothing without their drive, so CASCADE is safe there. `round_results → drive_rounds` stays RESTRICT on purpose, because results are records of what happened.

---

## 9. Explicit indexes on foreign keys and filter columns
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- Every FK column is indexed, either by its own index or as the first column of a PK/UNIQUE index.
- Extra indexes on `drives.status`, `applications.status`, `audit_logs (entity_type, entity_id)` and `audit_logs.created_at`.

**Alternatives:** Rely on primary keys only.

**Why:** Postgres indexes primary keys and UNIQUE constraints automatically, but **not** foreign keys. Without these indexes, joins like "applications of student X" and the RESTRICT checks on delete would scan whole tables. We don't add a separate `applications.drive_id` index, because `UNIQUE (drive_id, student_id)` already starts with `drive_id`.

## 10. Fixed branch codes, NOT NULL drive criteria, final withdrawal
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- `branch` must be one of `CSE, IT, ECE, EEE, ME, CE`. A CHECK enforces this on both `student_profiles` and `drive_branches`.
- `min_cgpa`, `max_backlogs` and `graduation_year` on drives are NOT NULL. "No cut-off" is `min_cgpa = 0`.
- Withdrawal is final: `UNIQUE (drive_id, student_id)` blocks re-applying, and the API returns a clear message.

**Alternatives:**
- A free-text branch.
- A `branches` lookup table.
- Nullable criteria meaning "no limit".
- Reusing the withdrawn row when a student re-applies.

**Why:** With free text, "CSE" and "Computer Science" would silently fail to match. A lookup table is more than v1 needs, and adding a branch is a one-line migration. NOT NULL criteria keep `EligibilityService` free of "null means no limit" special cases. A final withdrawal keeps the status history simple and auditable.

## 11. Separate `INELIGIBLE` status with `status_reason`
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- Application status adds `INELIGIBLE`, used when an admin edits drive criteria and an existing application no longer qualifies.
- A nullable `status_reason VARCHAR(300)` holds the human-readable reason.
- `REJECTED` is kept only for company rejections in rounds.
- A blocked apply (not eligible, or blocked by a policy) creates **no row**. Its reason goes back in the API error response.

**Alternatives:**
- Reuse `REJECTED` for both cases.
- Delete the application.

**Why:** "The company rejected you" and "the rules changed after you applied" mean different things to a student, and a TPO needs to tell them apart in a dispute. Keeping the row, with a reason, plus an audit-log entry makes the change explainable and auditable (edge feature #2).

## 12. Flyway seed data with a demo BCrypt password
**Milestone:** 2 · **Date:** 2026-11-01

**Decision:**
- `V2__seed_demo_data.sql` inserts 1 admin, 6 students, 3 fictional companies, 5 drives and the 3 policy rows.
- Every account uses the demo password `Demo@1234`, stored as a BCrypt (cost 10) hash. The hash was generated once with Spring Security's `BCrypt` class, run through `jshell` outside the project.
- Rows are linked by natural keys, not hard-coded IDs, and deadlines are relative to `now()`.
- Policy defaults: `DREAM_OFFER` active at 10 LPA, `ONE_OFFER` and `MAX_OFFERS` inactive.

**Alternatives:**
- Seed from Java code at startup.
- Commit no seed data.
- Use a plain-text password.

**Why:** A migration gives every fresh database the same realistic data, which makes eligibility demos interesting from day one. Natural-key joins keep the script independent of identity values. Relative deadlines keep OPEN drives open whenever the DB is recreated.

**⚠️ Before deployment (Milestone 12):** the demo password is public (it's in the README). The production admin must be created from **environment variables** (for example `ADMIN_EMAIL` and `ADMIN_PASSWORD`, hashed at startup), and the demo seed must not run in production. One way is to move it to a separate Flyway location that only the dev profile enables.

## 13. `ddl-auto: validate` with hand-written entities
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Switch `spring.jpa.hibernate.ddl-auto` from `none` to `validate`.
- Entities use `Short` for `SMALLINT` columns, `BigDecimal` for `NUMERIC`, `Instant` for `TIMESTAMPTZ`, `LocalDate` for `DATE`, and `@Enumerated(STRING)` for enums.
- `drive_branches` is mapped as an `@ElementCollection` of the `Branch` enum on `Drive`.

**Alternatives:**
- Keep `none`.
- Use `Integer` for `SMALLINT`.
- Map `drive_branches` as a separate `@Entity`.

**Why:** `validate` makes Hibernate compare entities with the Flyway schema at startup and refuse to start on a mismatch (a missing column, a wrong type), without ever changing the schema. It catches mapping bugs on day one instead of on the first query. `Integer` against `SMALLINT` fails validation, so the entity uses `Short` and DTOs convert. Branches have no identity of their own, so an element collection is simpler than a separate entity.

## 14. One global exception handler, with the DB as a backstop for conflicts
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- A single `@RestControllerAdvice` returns `{timestamp, status, error, message, path}` for every error:

| Status | Cases |
|---|---|
| 400 | validation, malformed JSON, wrong parameter type, unknown sort field |
| 404 | not found, unknown URL |
| 405 | wrong method |
| 409 | `ConflictException`, plus DB constraint violations mapped from the constraint name to a friendly message |
| 500 | everything else: generic message, stack trace logged on the server only |

- Services check business conflicts first (duplicate name, company has drives). The DB constraint is the backstop for race conditions.

**Alternatives:**
- Per-controller `try/catch`.
- Spring's default error JSON or `ProblemDetail`.
- Relying only on DB constraints.

**Why:** Clients (the React frontend, Postman) can rely on a single error shape. Service checks give the clearest messages, and the DB constraint guarantees correctness when two requests race. Without the extra 400/404/405 handlers, the catch-all would wrongly report client mistakes as 500s.

## 15. `PageResponse<T>` and capped page sizes
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Lists return `PageResponse<T>(content, page, size, totalElements, totalPages)`.
- Page size defaults to 20 and is capped at 100 (`spring.data.web.pageable.*`).
- Pages are 0-based, and a size larger than 100 is quietly capped.

**Alternatives:**
- Return Spring's `Page` directly.
- Use custom `page`/`size` parameters.

**Why:** Spring's `Page` JSON is an internal structure that can change between versions, and Spring Data itself warns against serialising it. Our own record is a stable API contract for the frontend. The cap stops a client from asking for 1 million rows.

## 16. Known limitation: company name uniqueness is case-insensitive only in the service
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- `CompanyService` rejects duplicate names ignoring case (`existsByNameIgnoreCase`).
- The DB constraint `uq_companies_name` is case-sensitive.
- We are **not** adding a `lower(name)` unique index for now.

**Alternatives:** A `V3` migration that replaces the constraint with `CREATE UNIQUE INDEX ... ON companies (lower(name))`.

**Why:** Only TPO admins create companies, so concurrency is very low. Two simultaneous creates of "Acme" and "acme" are the only way to get past the check, and that is unlikely. In a 10-parallel-request test, the service check caught all 9 duplicates. Revisit this if more roles can create companies.

## 17. Entity → DTO mapping happens inside `@Transactional` service methods
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Services return DTOs, never entities.
- Hand-written `@Component` mappers (for example `CompanyMapper`) also trim input and turn blank strings into `null`.

**Alternatives:**
- Map in controllers.
- Turn `open-in-view` back on.
- Use MapStruct.

**Why:** With `open-in-view: false` and LAZY relationships (Drive → Company), touching a lazy field after the transaction ends throws `LazyInitializationException`. Mapping inside the transaction makes that impossible, and it keeps entities out of the web layer. MapStruct isn't in our stack, and hand-written mappers are easy to read and explain.

## 18. Drive status transitions as explicit endpoints, with the rules in one map
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Status changes only through `POST /api/drives/{id}/open | /close | /complete`. `PUT` never changes the status, and a new drive always starts as `DRAFT`.
- All the rules live in `DriveService`:
  - `ALLOWED_TRANSITIONS` = DRAFT→OPEN, OPEN→CLOSED, CLOSED→COMPLETED.
  - `EDITABLE_STATUSES` = DRAFT, OPEN.
  - `checkCanOpen()`: the deadline must be in the future and there must be at least one branch.
- `checkCanOpen()` runs again whenever an OPEN drive is edited, so an OPEN drive can never become invalid.
- Every blocked change is a 409 that names the allowed next step.

**Alternatives:**
- Let `PUT` change `status`.
- A generic `PATCH {status}`.
- Put the rules in the entity or spread `if`s across methods.

**Why:** Each endpoint is one clear action, which is easy to secure per role later and easy to audit. Keeping the rules in one map makes them easy to read, explain and test: 12 parameterised cases cover every from → to combination. The unit tests use their own hand-written list of allowed transitions, so they would catch a wrong entry in the map.

## 19. Avoid N+1 on the drives list: `@EntityGraph` for company, `@BatchSize` for branches
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- `DriveRepository.search` uses `@EntityGraph(attributePaths = "company")`.
- `Drive.branches` has `@BatchSize(size = 100)`.
- The filters are optional JPQL parameters (`:status IS NULL OR ...`).

**Alternatives:**
- `JOIN FETCH` both the company and the branches.
- A global `hibernate.default_batch_fetch_size`.
- Turn on EAGER fetching.

**Why:** It was measured with SQL logging on 5 drives:

| | Queries per request |
|---|---|
| Before | 9: 1 for the drives, 3 for companies, 5 for branches. It grows with page size, so about 200 for 100 drives. |
| After | 2: drives JOINed with companies, then one `drive_id = any(?)` query for the branches. A `count(*)` is added when there's more than one page. |

The company is a many-to-one, so JOINing it keeps one row per drive and paging still works in SQL. The branches are a collection: `JOIN FETCH` with paging makes Hibernate load every row and page them in memory (warning HHH90003004), so they're batch-loaded instead. EAGER would load them everywhere, even where they aren't needed.

## 20. `CurrentUserProvider` interface with a temporary demo-admin implementation
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:**
- Services ask `CurrentUserProvider.currentUserId()` who is calling.
- Until Milestone 5, `DemoAdminCurrentUserProvider` returns the id of `admin@placementhub.dev`, looked up by email. It is marked TODO for Milestone 5.
- `createdBy` uses `getReferenceById`, which doesn't need an extra SELECT.

**Alternatives:**
- Hard-code `createdBy = 1`.
- Make `created_by` nullable.
- Build JWT login now.

**Why:** `DriveService` depends on *what* it needs (the current user's id), not *how* it is found. In Milestone 5 we add a JWT-based implementation and delete the demo one, and the services and their tests don't change. In tests we just mock the interface. Looking the admin up by email avoids relying on identity values.

## 21. Injected `Clock` for time-based rules
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:** A `Clock` bean (`Clock.systemUTC()`) is injected into services. Services call `Instant.now(clock)`, never `Instant.now()`.

**Alternatives:** Call `Instant.now()` directly.

**Why:** Rules like "the deadline must be in the future" depend on the current time. With a fixed `Clock` in tests, these rules are tested exactly, including the "deadline is exactly now" edge case, without flaky time-dependent tests. This will matter again for "withdraw before the deadline" in Milestone 4.

---

## 22. Known limitation: unknown enum values in a JSON body give a generic 400
**Milestone:** 3 · **Date:** 2026-11-01

**Decision:** For now, a body like `"branches": ["XYZ"]` returns 400 "Malformed JSON request body", without naming the field.

**Alternatives:** Inspect Jackson's `InvalidFormatException` in the handler and say, for example, "Invalid value 'XYZ' for branches. Allowed: CSE, IT, ...".

**Why:** The status code is correct and the request is rejected safely. The friendlier message is a small improvement best done in the Milestone 11 testing pass, or when the frontend needs it (the frontend sends enum values from dropdowns, so this is rare).
